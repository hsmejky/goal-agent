# Audit: how plugin-maintainer's issues fared with the Engineering skills

Answers goal-agent ticket [#3](https://github.com/hsmejky/goal-agent/issues/3) (map [#1](https://github.com/hsmejky/goal-agent/issues/1)).
Audited 2026-10-14 against `hsmejky/ai-plugin-manager` at `8606e2d` (local `main`) and its GitHub issues #1-#72, and mattpocock-skills 1.3.1.
Read-only: nothing in `ai-plugin-manager` was written.

Base URLs: issues `https://github.com/hsmejky/ai-plugin-manager/issues/<n>`, commits `https://github.com/hsmejky/ai-plugin-manager/commit/<sha>`.
Statements marked **(inference)** are my reading, not something a source states.

## Summary

- The agent definition is `.claude/agents/plugin-maintainer.md` (added in PR [#18](https://github.com/hsmejky/ai-plugin-manager/pull/18), commit `fba617a`).
  It tells the agent to file every gap as an issue labelled `P1`-`P4` plus `ready-for-agent` or `needs-info`.
- 59 issues exist (excluding PRs). All 59 carry `ready-for-agent` (current label set), none carries a category label (`bug`/`enhancement`), and only 3 ever passed through `needs-triage` (#38, #39, #40).
  Five were filed `needs-info` and flipped to `ready-for-agent` after the user decided (#27, #29, #31, #57, #59).
- The issues *were* workable: all 38 maintainer-era issues (#19-#60, excluding PR numbers) are closed, fixed by integration-branch PRs ([#37](https://github.com/hsmejky/ai-plugin-manager/pull/37), [#48](https://github.com/hsmejky/ai-plugin-manager/pull/48), [#52](https://github.com/hsmejky/ai-plugin-manager/pull/52), [#56](https://github.com/hsmejky/ai-plugin-manager/pull/56)), usually the same day.
  So the fit broke at the *conventions* (labels, brief shape, vocabulary), not at "an agent can't work these issues".
- No trace that the Engineering `triage` skill ever ran on them as written (no disclaimer, no `## Agent Brief` comment). The only visible Engineering-skill use is the setup-skill chain #57-#71, where `to-spec`, `to-tickets` and `implement-spec` produced and consumed issues in their native shape.

## 1. What the definition promises

Source: `.claude/agents/plugin-maintainer.md` at [`8b7d54e`](https://github.com/hsmejky/ai-plugin-manager/commit/8b7d54e) (the "generalize" revision; the issue rules did not change from `fba617a`).

| Rule | Text (condensed) |
| --- | --- |
| Labels | "one of `P1`-`P4` ..., plus `ready-for-agent` when the body is a complete brief or `needs-info` when it needs a user decision" |
| Body | "the gap, the evidence (source, Host version, command and output), why it matters, and done when. State what must become true; the design belongs to whoever runs the issue." |
| Dedup | check `gh issue list --state all` first; comment new evidence on an open issue |
| Closing | only issues it created, only when the gap vanished without a repo change |
| Writes | only `state.md` and issues; code, tests, docs are the user's |
| Priority map | `docs/agents/triage-labels.md`: P1 verification fails / Host break, P2 Host release unprocessed, P3 docs mismatch, P4 research finding; objective-5 features take the user's priority or P3 |

The definition never mentions `needs-triage`, a category label, the `triage` skill, or the AGENT-BRIEF format. `docs/agents/triage-labels.md` keeps the five default roles unchanged and appends the P-table as an extension.

## 2. Who filed what, and how it was worked

### 2.1 Authorship is not recoverable

Every issue and every label event (checked on the timelines of 57 issues) has actor `hsmejky`; the agent and the user act through one GitHub account.
So "filed by the agent" can only be **inferred** from content (the `Gap / Evidence / Why it matters / Done when` form) and from `state.md` commit messages ("filed #57-#60", [`86a31de`](https://github.com/hsmejky/ai-plugin-manager/commit/86a31de)).
The `triage` skill requires every comment to start with `> *This was generated by AI during triage.*`; that string occurs in no issue or comment (0 of 59), which is the one marker that would have separated agent output from user output.

### 2.2 Three generations of issues

| Generation | Issues | Shape | Source of the shape |
| --- | --- | --- | --- |
| Pre-agent (2026-10-13 to 07:52 UTC 10-14) | #2, #11 (specs); #3-#9, #12-#15 | spec: `Problem Statement / Solution / User Stories ...`; tickets: `Parent / What to build / Acceptance criteria` | to-spec / to-tickets form (**inference**: headings match; PR [#10](https://github.com/hsmejky/ai-plugin-manager/pull/10) closes #2-#9 as one set) |

| Setup-skill chain | #57-#60 then #64-#71 | #60 maintainer form; #71 `to-spec` form; #64-#70 `Parent / What to build / Acceptance criteria` | PR [#63](https://github.com/hsmejky/ai-plugin-manager/pull/63) says the spec "lives in issue #71 in `to-spec` form ... ready for `implement-spec`" |

### 2.3 How they were worked

- Maintainer-era issues were closed by "integration branch" PRs whose body is `Closes #n` lines plus "implemented ticket by ticket (one branch per issue, merged here)" ([#37](https://github.com/hsmejky/ai-plugin-manager/pull/37)); commit logs show `Merge ticket/<n>-...`, `Merge fix/review-findings (code review fixes)`.
  This is the shape `implement-spec` prescribes (integration branch, one branch per ticket, merger, then `code-review`) **(inference)**; it was applied to a *list of issues*, not a spec, since #19-#55 have no parent spec issue.
- #64-#70 + spec #71 closed by PR [#72](https://github.com/hsmejky/ai-plugin-manager/pull/72) (`closingIssuesReferences` 64-71), the one explicit `implement-spec` run (PR #63 text).
- `wayfinder`: 0 mentions. `tdd`: no issue/PR text names it; `test:`/`feat:` commit prefixes are consistent with it but prove nothing **(inference)**.
- Research issues (#25, #26, #33, #35, #58) were answered by PRs adding `docs/research/*.md` ([#16](https://github.com/hsmejky/ai-plugin-manager/pull/16), [#62](https://github.com/hsmejky/ai-plugin-manager/pull/62), commit `8ca6469`) and a "Done in #62: ..." comment (#58). That is the same convention as this repo's `research` skill.

## 3. Where the fit broke

### 3.1 State labels: no `needs-triage` entry, all `ready-for-agent`

Evidence (timelines via the GitHub API):
- #19-#26, #28, #30, #32-#36, #41-#47, #49-#51, #53-#55, #58, #60: `ready-for-agent` applied at creation, no `needs-triage` ever.
- #38, #39, #40: `needs-triage` then, at 10:46:38Z (#38) in the same instant, `P1`/`P4` + `ready-for-agent` and `needs-triage` removed; a comment `-- Triage (PR #37 review, 2026-10-14): P1 ...` follows. So `needs-triage` appears as a 20-minute holding state, only for findings from a PR review.
- #27, #29, #31, #57, #59: `needs-info` + P-label at creation; after the user's answer `ready-for-agent` added and `needs-info` removed. Skill-consistent (`needs-info` = waiting for a decision, then `ready-for-agent`), with two wrinkles below (3.4).
- Result: 59/59 issues carry `ready-for-agent` today (label count), including ones filed as questions to the user.

Misfit with the skills: `triage` treats `needs-triage` as the entry state for anything unlabeled and shows "Unlabeled / needs-triage" buckets first. Issues that arrive pre-labelled never appear in `/triage`'s attention list; the user's triage pass is bypassed by design (definition: `ready-for-agent` "when the body is a complete brief"). This is the exact question of ticket #5; the data says it works mechanically but removes the user's verification step. Whether that is wanted is a design choice, not an error **(inference)**.

### 3.2 No category label

`triage` wants "exactly one category role and one state role" per issue. 0/59 issues carry `bug` or `enhancement` (both labels exist in the repo as GitHub defaults; `gh label list`). The agent's P-label partly encodes category: P1 verification, P2 releases, P3 docs, P4 research, so category is *implicit in priority* (see 3.3).

### 3.3 P1-P4 is outside the vocabulary and has drifted

Label counts across 59 issues: `P1` 7, `P2` 1, `P3` 12, `P4` 18, none 21 (pre-agent issues and #71).

- Declared as "by the objective the gap is against" (`docs/agents/triage-labels.md`), i.e. a *category*, but named and used as a *priority rank*; the definition itself says "Raise the priority of a security or blocking gap".
- Drift: `P4` is declared "A research finding that would change the project", yet 18 issues carry it and only #25, #26, #33 are research. The rest are small bugs or features (#32 short-SHA refs, #36 `[features] plugins = false`, #41-#44, #47, #50, #54). In practice P4 = "low". **(inference)**
- Contradiction: #53 is `P2` although P2 is declared "A Host release is not yet processed"; its body says "Raised to P2 as a security/machine-safety gap".
- Feature gaps default to `P3` ("docs do not match reality") per the table's fallback; #57-#60 and #64-#70 got `P3`, then someone removed `P3` from #64-#70 at 13:46:52Z (`unlabeled:P3`), leaving the slices without any P-label. The label was meaningless for them.
- The skills ignore unknown labels, so there is no hard conflict (`grep` for priority or P1-P4 in the 1.3.1 `triage`, `to-tickets` and `implement-spec` skills finds nothing; triage names only five states and two categories). The cost is that nothing the user runs consumes P-order; ordering lives in `state.md` "What next" instead.

### 3.4 Brief shape versus AGENT-BRIEF

AGENT-BRIEF (`skills/engineering/triage/AGENT-BRIEF.md`): a *comment* posted when the issue moves to `ready-for-agent`; sections Category / Summary / Current behavior / Desired behavior / Key interfaces / Acceptance criteria / Out of scope; durable (no file paths, no line numbers), behavioural, explicit scope boundaries.

| AGENT-BRIEF element | Maintainer issues (#19-#60) |
| --- | --- |
| Posted as comment at `ready-for-agent`; body is context | The body *is* the brief; briefs appear as comments only in #29 (decision comment) and appended into the body of #27 ("## Brief (after the decision of 2026-10-14)"). 0 issues have a `## Agent Brief` heading. |
| Category | 0/59 |
| Current behavior | `## Gap` + `## Evidence` (good match, richer: Host version, command, output) |
| Desired behavior | `## Done when` (53/59 issues have a Done-when/Acceptance section); states what must become true, per definition |
| Key interfaces | absent as a section; sometimes inline |
| Acceptance criteria | Done-when bullets: partial match, often phrased as outcomes, not independently testable lines |
| Out of scope | 1 of the 30 `Gap`-form issues (#60); otherwise only specs and pre-agent tickets (#2, #11, #12, #15, #71) |
| No paths, no line numbers | 42 issues name file paths in backticks; 13 cite `file:line` (e.g. #19 `checks/marketplace-plugins.mjs:58`, #44 `live-skills.mjs:22-36`, also #20, #22, #23, #41-#43, #45-#47, #49, #51) |

Verdict: the maintainer form is a *second* brief format. It is stronger on evidence and weaker on scope boundaries and durability. A `ready-for-agent` issue still carries `Decision needed` headings (#27, #29), so the body no longer reads as an instruction **(inference)**.

### 3.5 Umbrella issues versus vertical slices

#22 (7 numbered groups: "Many claims about Host behaviour ... are neither covered by a test nor listed as a manual check"), #24 (9 items, "Docs mismatches found in the 2026-10-14 audit"), #45 (4 items) are bundles; follow-ups were split off after the fact ("Follow-up of #22 (groups 1 and 2), split off per its Done-when clause", #38; #39/#40 likewise). `to-tickets` wants independently grabbable slices with explicit blocking.
The maintainer never uses native sub-issue or blocked-by edges: blockers are prose ("Blocked by #22", #38 triage comment; "Blocked by #57 ... and #58", #60). Only #64-#70 use native edges (PR #63 text: "native blocked-by edges"), created by `to-tickets`.

### 3.6 Retractions and accreted evidence

The agent's evidence arrives as later comments, some withdrawing earlier ones: #20 comment 3 ("Correction to my previous comment"), #22 comment 3 ("Withdrawn: 'the project-only declaration ...'"), state.md commit `e4d4adb` "project-only auto-upgrade claim corrected on #20, #22, #31". Result: the authoritative brief is split across body and 3 comments. AGENT-BRIEF's "the brief is the contract" would want one current brief **(inference)**.

### 3.7 Terminology collision

The definition and `triage` use different "maintainer": in `triage` it is the human who owns the repo; the plugin-maintainer *agent* headed its #29 comment "Maintainer triage (2026-10-14)", while the user answered #57 and #59 with "Maintainer answer(s)" and "grilling session" (comments, same account). Agent and human both write as "maintainer" on one thread **(inference: confusing, not harmful)**.

### 3.8 Duplicates and stale issues

- Duplicate: none refiled. One overlap, flagged by the agent itself: #24 item 4 and #27 (`#24` comment "Item 4 ... is now also covered by #27"). #50 then #54 and #34 then #32 are progressive refinements, not duplicates.
- Stale: nothing. The whole history spans 2026-10-13T23:47Z (#2) to 2026-10-14T13:58Z (#72). The maintainer-era issues mostly closed within hours, e.g. #19 08:32Z to 10:59Z.
  The audit cannot test "sits in `ready-for-agent` for weeks", the case AGENT-BRIEF's durability rules target.
- Open now: #64-#71 (all `ready-for-agent`), all covered by PR #72.

### 3.9 state.md versus reality

- Last commit [`86a31de`](https://github.com/hsmejky/ai-plugin-manager/commit/86a31de), "What next": `#58, #57, #59, #60`. Reality (GitHub): all four closed by 13:49Z; open issues are #64-#71 and PR #72; state.md mentions none of them or PRs #61-#63, #72. Objective 5 requires `state.md` to record a feature's issues "and their state" while it is unfinished, so it is stale by the maintainer's own rule. Cause: `state.md` is committed only by maintainer sessions (user-started) and the user ran #57-#60 between sessions (**inference**).
- Format drift: the definition lists four sections in a fixed order (Hosts, Watching, Watch list, What next). The file has a fifth thing: a ~3,000-character single-line "Last session" paragraph holding a session log in the header; 16 commits touch the file, mostly `state:` commits that prepend to it (`git log --follow -- state.md`, [`e438c36`](https://github.com/hsmejky/ai-plugin-manager/commit/e438c36) first baseline to `86a31de`).
- Git history of `state.md` shows it doubles as a *triage ledger*: messages such as `#29 triaged ...`, `#31 decided ... now ready-for-agent` ([`36e17a0`](https://github.com/hsmejky/ai-plugin-manager/commit/36e17a0)), `#38-#40 triaged` ([`27a9a96`](https://github.com/hsmejky/ai-plugin-manager/commit/27a9a96)). The agent performs a triage role (priority, readiness, deciding what the user must answer) that `triage` assigns to the user's pass **(inference)**. That is evidence for ticket #5 and #8.

## 4. What fit

- `needs-info` as "waiting for the user's decision" and the flip to `ready-for-agent` with the decision recorded (#27, #29, #31, #57, #59) matches the skill's state machine.
- Evidence-first `Gap` bodies and `Done when` are close to Current behavior + Acceptance criteria; the maintainer's rule "state what must become true; design belongs to the implementer" equals AGENT-BRIEF's "behavioral, not procedural".
- Research issues resolve into dated notes in `docs/research/` and a closing comment, matching how this project's `research` skill is used.
- `to-spec`/`to-tickets`/`implement-spec` consumed the setup-skill work cleanly (#71, #64-#70, PR #72) once the feature was shaped as a spec; the maintainer's #57-#60 are the front half (decide, research, spec request) of that chain.
- `docs/agents/issue-tracker.md` in `ai-plugin-manager` already includes the wayfinding section (native sub-issue / blocked-by edges),; the maintainer-era issues do not use it (prose blockers), #64-#71 do.

## 5. Implications for the map's other tickets (inference)

- #5 (entry via triage vs direct): the data supports "direct `ready-for-agent`" mechanically (fast closure) but shows the cost: no category, no AGENT-BRIEF block, no triage comment, no human verification; `needs-triage` was used only for PR-review findings.
- #6 (priority axis): P-labels drifted from category to rank and are read by no skill; state.md "What next" carries the real ordering. Candidates: keep P as an extension but define it as pure rank, or drop it for ordering in state.
- #7 (state location): state.md went stale against the issue tracker within hours and mixes in a session log and triage ledger; the tracker already holds the ground truth (labels, closure, sub-issues).
- #8 (shared config): `triage-labels.md` extension worked without breaking skills; collisions were terminological ("maintainer", `P3` fallback), not file-level.
- Possible new ticket: how a Goal agent's output is distinguished from the user's when both use one GitHub account (the `triage` disclaimer is the only marker and the agent did not use it).
- Possible new ticket: whether `to-tickets` slices (parent spec, native blocked-by) should be the Goal agent's output for multi-issue work instead of flat `Gap` issues, since #64-#71 show that shape closing cleanly.

## Method and limits

- Issue data: `gh issue list --state all --limit 200`, `gh issue view`, timeline API for 57 issues; PR data from `gh pr list --state all --limit 100`.
- Counts are over the 59 issues returned (all of #2-#71 that are issues); numbers #1, #10, #16-#18, #37, #48, #52, #56, #61-#63, #72 are PRs.
- Label counts reflect current labels, plus timelines for history; edits to issue bodies are not versioned in this audit, so "body appended later" (#27) rests on the body text itself.
- Not examined: PR review comments, CI logs, and the content of the research notes beyond their issue links.
