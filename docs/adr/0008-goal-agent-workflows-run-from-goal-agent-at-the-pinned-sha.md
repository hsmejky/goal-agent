# Goal agent workflows run from goal-agent at the pinned SHA; the contract text and callers are rendered and checked; the guard stays copied

The gate, the Consultation, the audit and the staleness check run from goal-agent as composite actions (`hsmejky/goal-agent/.github/actions/<unit>@<sha>`), at the full 40-hex SHA written in the caller's `uses:` line. No gate or Home workflow script is copied into a Covered repo or a Home repo any more. GitHub downloads the action's repository at that SHA, and each action runs goal-agent's scripts from `github.action_path` ("The path where an action is located. This property is only supported in composite actions.", [Contexts reference][ctx]), so the scripts that run come from the `uses:` commit by construction, with no second SHA to keep in step and no checkout of goal-agent. The SHA is the shared `goal-agent-pin`: a full commit SHA on goal-agent's `main` (a tag may follow only as a comment), the same in every `uses:` line of a Home repo's callers and of each Covered repo's callers, and the same across all Home repos covering one Covered repo (literal equality, per [#94][i94]). A Covered repo keeps two thin callers (gate and Consultation) and a Home repo keeps thin callers for the audit, the staleness check, the drift check and the sync. Each caller holds its trigger, `permissions`, `if`, `concurrency` and `runs-on`, and its job has exactly one step: the `uses:` of the action. Values handed to an action, as `with:` inputs or as the calling step's `env`, are visible to every step inside the action, and any other step in the caller job would run alongside them. The action therefore does its own checkout of the caller repo (default branch, `persist-credentials: false`, nothing from the PR) and its own Node setup, and its internal steps are goal-agent code plus third-party actions pinned by full SHA and reviewed in goal-agent. Secrets go by explicit name: the calling step's `env` names each agent's `GOAL_AGENT_<NAME>_FIRE_TOKEN` and `GOAL_AGENT_<NAME>_TRIGGER_ID`, one pair per installed agent; if a live run shows the step `env` does not reach the action's script step, the pairs go as declared `with:` inputs that the action maps to `env` on its script step only. Never `secrets: inherit` or `toJSON(secrets)`. Trust ([R37][r37]) is unchanged: `pull_request_target` runs the caller from the default branch, and the action is fetched at the immutable SHA in that caller and runs nothing from the PR. The audit and staleness actions take no secrets and use the caller's `GITHUB_TOKEN`.

This answers [ADR 0006][adr6]'s rejection of "Home repos fetch a pinned version when they run" for these workflows. A full SHA in the `uses:` line is immutable, and it is reviewed in the caller's PR like any other change, so a pin bump is visible and auditable in that repo; in a Home repo, the audit of `main` ([R50][r50]) sees it like any other change. GitHub fetches the action for an Actions job, not the agent's session, so no code reaches the session by a network fetch. The guard, the one thing that runs inside the session, stays a committed copy on the Home repo's `origin/main` ([R45][r45]): `scripts/guard/` and the shared modules it imports (moved to `scripts/lib/`), byte-identical to goal-agent at the pin, with `.claude/settings.json` from `templates/home-settings.json` at the pin.

The caller files are rendered, not hand-copied. `templates/` at the pin holds the canonical caller files, and Appendix E of the [design][design] names them as each Covered repo's and Home repo's workflow text. Their only parameters are the `uses:` SHA and, in the gate and Consultation callers, one secret-pair block per agent in the Covered repo's registry. Each rendered caller is checked: a Home repo's callers by its drift check, and a Covered repo's callers by the gate action itself, which renders both templates from its own commit for the agents in the checked-out registry, compares them with the default branch's files, and on drift still sets `goal-agent-review` from its evaluation, then fails the job with the differing lines. A Home repo's `GITHUB_TOKEN` cannot read a private Covered repo, so the cross-repo shared-pin check (each Covered repo's `uses:` SHA against each Home repo's pin) stays [R59][r59]'s hand procedure.

The contract text is rendered and checked against the pin, not adopted and edited. A drift check in each Home repo renders Appendices A–C and the R59 checklists from the design at `goal-agent-pin`, applies exactly the substitutions R59 lists (issue [#107][i107]) and nothing more, and fails when the Home repo's contract, checklists, operations section, definition skeleton (its fixed lines, in order), guard copy, settings or callers differ, or when a `uses:` SHA differs from the pin. Any edit outside the Home-owned parts R59 lists is drift; Home-specific rules go to the Home repo's CLAUDE.md or the definition. A sync workflow that the user starts by hand with a target commit renders the same files at that commit, sets the pin and every `uses:` SHA to it, recopies the guard and opens a PR; the Covered repo side of a bump stays a hand PR that changes its two `uses:` SHAs.

This ADR supersedes ADR 0006 for the gate, Consultation, audit and staleness workflows: they are no longer copied and pinned, but called at the pin. It amends ADR 0006 for the contract text: the text is still a committed file in the Home repo pinned by `goal-agent-pin`, but rendered from the design at the pin and checked, not hand-adopted. It keeps ADR 0006 for the guard: tested here, copied into each Home repo, pinned, and run from the copy on `origin/main`, never fetched at run time.

## Considered Options

- **Copied scripts, the status quo ([ADR 0006][adr6])**: rejected because every design change is hand-copied into each Home repo and Covered repo, which produced re-adoption issues ([#84][i84], [#85][i85], [#103][i103]), and nothing checks that a copy matches its source word for word. A second Home repo doubles the copies.
- **Reusable workflows** (`uses: hsmejky/goal-agent/.github/workflows/<unit>.yml@<sha>`): not chosen. A called workflow keeps the caller job to one `uses:` line with no steps, which is its real advantage. But "When a reusable workflow is triggered by a caller workflow, the `github` context is always associated with the caller workflow" ([Reusing workflow configurations][reuse], § `github` context), so `github.workflow_sha` names the caller's commit, and the called workflow needs another way to check out goal-agent at its own commit. GitHub's [Contexts reference][ctx] now documents one: `job.workflow_sha`, "The commit SHA of the workflow file that defines the current job. (not available on GitHub Enterprise Server)", and `job.workflow_repository`, "The `owner/repo` of the repository containing the workflow file that defines the current job.", with an example of a reusable workflow checking out its own source with `repository: ${{ job.workflow_repository }}` and `ref: ${{ job.workflow_sha }}`. That removes the main reason reusable workflows needed OIDC, so this option is viable. It still loses on these costs:
  - The self-commit is a second checkout, guarded by a step that compares `git rev-parse HEAD` and the repository with `job.workflow_sha` and `job.workflow_repository` and fails before any script runs. With a composite action the same-commit property needs no guard step, because nothing is checked out.
  - `job.workflow_sha` is not yet verified on a live `pull_request_target` and `issue_comment` run. Choosing reusable workflows would require that run first.
  - A called workflow reads only the secrets declared under `on.workflow_call.secrets` (or every secret, with `secrets: inherit`, rejected below), so a Covered repo's agents need numbered optional slots (`agent_1_fire_token`, `agent_1_trigger_id`, … `agent_4_*`) plus an `agents` input naming them in slot order. A slot without a name, or a name without its slot, would fail the run, and a fifth agent on one Covered repo would be a goal-agent change. The composite action takes each agent's pair by name with no slots.
  - "The `GITHUB_TOKEN` permissions passed from the caller workflow can be only downgraded (not elevated) by the called workflow" ([Reusing workflow configurations][reuse]), so the caller still holds the permissions, as well as the triggers, and its file is still a copy that has to be rendered and checked. The smaller caller saves less than it seems.

  If reusable workflows are ever kept, for one unit or all, `id-token: write` with the OIDC `job_workflow_sha` claim stands only as a fallback, used only if the live run shows `job.workflow_sha` unusable, never as the default. It adds a permission to every gate job on `pull_request_target`, against R59's rule that each step reads only what it names. When used, it is a required caller line in the templates, R59's checklists and Appendix E, so the drift check catches a missing one. A missing claim fails the run loudly with a message naming the missing permission, and the called workflow never falls back to a default ref.
- **Fixed minimal caller templates, stated but not compared**: rejected because the job wrapper would become a new unchecked hand copy, which is the problem this ADR removes. A dropped permission or a changed trigger would silently weaken the gate.
- **Branch or tag refs in `uses:`**: rejected because both are mutable, so a `pull_request_target` job with a write token would run whatever the ref points to at run time, unreviewed in the caller's repo.
- **`secrets: inherit`, or `toJSON(secrets)` passed to an input**: rejected because code from goal-agent would receive every secret in the Covered repo instead of the pairs it needs.
- **Dependabot or Renovate bumps of goal-agent refs**: rejected because a bot bump in one repo breaks the shared pin across the Home repos and Covered repos that must name the same SHA. The sync PR is the bump path.
- **Git submodule of goal-agent in each Home repo or Covered repo**: rejected because cloud routines clone fresh and may not initialise submodules, and Claude Code reads `CLAUDE.md` and agent definitions from the working tree, so a missing submodule would fail silently: the session would run with no contract or no guard code rather than stop.
- **Plugin route**: deferred to [#101][i101]. If it comes back "yes", its own ADR may replace the guard copy and the rendered contract; nothing here blocks that.

## Consequences

- A gate or Home workflow fix reaches a repo by changing one SHA in its callers, not by recopying scripts. `.github/scripts/goal-agent-review/` goes away from Covered repos, and `scripts/gate/` and `scripts/home/` from Home repos.
- Every pin bump, text-only included, needs the two-line `uses:` SHA PR in each shared Covered repo, merged in the same sitting as the Home repo sync PRs. [#94][i94]'s "only if `scripts/gate/` changed" economy is dropped so that the shared-pin check stays literal equality.
- A Covered repo's drift is now a `uses:` SHA that differs from the shared pin, or a caller that differs from its rendered template. The gate action reports the second on every PR; R59's hand procedure checks the first.
- The drift check cannot be a required status on a Home repo's `main`, because the agent pushes `memory/` there directly ([R18][r18]). A failure on push opens or updates one issue in the Home repo, as the staleness check does.
- A sync PR opened with `GITHUB_TOKEN` starts no workflows, and opening it needs the repo setting "Allow GitHub Actions to create pull requests". R59 tells the user to start the drift check on the PR before merging.
- If GitHub cannot fetch the action at the pinned SHA, the job fails and the gate stays red: a loud failure, not a silent fallback.
- The caller templates, R59's checklists, R25, R38, Appendix D and Appendix E change to describe this setup in the tickets that build it. ADRs 0001–0005 and 0007 stay as written; ADR 0007's guard fix still reaches a Home repo by recopying the guard at a new pin.
